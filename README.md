# create-svelte

Everything you need to build a Svelte project, powered by [`create-svelte`](https://github.com/sveltejs/kit/tree/main/packages/create-svelte).

## Creating a project

If you're seeing this, you've probably already done this step. Congrats!

```bash
# create a new project in the current directory
npm create svelte@latest

# create a new project in my-app
npm create svelte@latest my-app
```

## Developing

Once you've created a project and installed dependencies with `npm install` (or `pnpm install` or `yarn`), start a development server:

```bash
npm run dev

# or start the server and open the app in a new browser tab
npm run dev -- --open
```

## Building

To create a production version of your app:

```bash
npm run build
```

You can preview the production build with `npm run preview`.

> To deploy your app, you may need to install an [adapter](https://kit.svelte.dev/docs/adapters) for your target environment.

## Backend CLI

Install the uv environment, then generate JSON schemas and TypeScript models
for classes marked with `@frontend`:

```bash
uv install
uv run ceynic generate-frontend-models
```

The command requires `json-schema-to-typescript`'s `json2ts` executable to be
available on `PATH`.

## Database migrations

The app uses PostgreSQL and async SQLModel. Alembic reads `DATABASE_URL` from the
environment (falling back to the project `.env`) and imports all table models
through `src/models/registry.py`. Migrations are run explicitly, not at app startup.

```bash
uv install
uv run alembic upgrade head            # new, empty database
uv run alembic revision --autogenerate -m "describe change"
uv run alembic upgrade head
```

Review every autogenerated revision before applying it; in particular, check
constraint names, defaults, nullable columns, and data migrations. The first
revision, `0001_existing_schema`, represents the PostgreSQL schema audited when
Alembic was introduced. `0002_align_model_constraints` brings that schema into
line with the models, including unique storefront content/PayPal settings and
deferred uniqueness for image positions.

### Adopting an existing database

1. Back up the database and compare its actual schema with
   `alembic/versions/0001_existing_schema.py`: all 13 tables, column types and
   nullability, primary/foreign keys (including `ON DELETE`), defaults, and
   unique constraints. In particular, `settings.id` and `paypal_settings.id`
   are integers, and the baseline's `product_images` unique constraint is
   **not** deferrable. Do not stamp a database that differs from this revision;
   reconcile its schema or write an environment-specific migration first.
2. Check for duplicate `contents.storefront_id`,
   `paypal_settings.storefront_id`, or non-null `refresh_tokens.user_id`, and
   orphaned `paypal_settings.storefront_id`. Check that no rows have NULL in
   columns changed to NOT NULL by `0002_align_model_constraints`. Resolve any
   issues before upgrading (the migration does not delete or replace data).
3. On a copy of the database first, stamp the **verified** baseline and upgrade:

   ```bash
   uv run alembic stamp 0001_existing_schema
   uv run alembic upgrade head
   uv run alembic current
   uv run alembic check
   ```

   Repeat against the target database once the copy succeeds. `stamp` only
   records the baseline revision; it does not create or alter tables. Do not run
   `upgrade head` on an existing database before stamping the verified baseline.

The audited database had no duplicates or NULLs that block the corrective
migration. Its initial schema had nullable fields and missing uniqueness/FK
constraints that are intentionally changed in revision 0002; review this
revision's table locks before running it on a busy database. Do not downgrade
past the baseline on a populated database: that downgrade drops all tables.
